## The product owner's answers

| # | Topic | Decision | Implemented in |
|---|---|---|---|
| 1 | Apple's certificate revocation check while an update installs (PLT-R906, section 13.7) | Accepted as the integrator recommended. While Sparkle installs an update, its installer `Autoupdate` checks the code signature of the downloaded app, and macOS asks Apple's OCSP service, on behalf of `Autoupdate`, whether the Developer ID certificate that signs it has been revoked. In run `20261123T055630Z-upgrade` the per-process packet capture (`tcpdump` on the PKTAP interface) showed a DNS lookup of `ocsp2.g.aaplimg.com`, the name of Apple's content delivery network behind `ocsp2.apple.com`, made by the system resolver `mDNSResponder` for `Autoupdate`, then a connection to `17.253.61.136` on TCP port 443 sent by macOS's trust service `trustd` with `Autoupdate` as the effective process (`proc trustd`, `eproc Autoupdate`), not from a socket of `Autoupdate` itself; the earlier runs of the day showed the same check (a connection to `17.253.61.142` in run `20261123T020752Z-upgrade`, the lookup in run `20261123T004514Z-upgrade`). macOS makes this check for any signed app, and the app adds no data to it. The specification now allows it explicitly and names it: who makes it (macOS's trust service `trustd`, on behalf of `Autoupdate`), when (from the download of the update archive until the updated app has relaunched), which service (`ocsp.apple.com`, `ocsp2.apple.com` and the names under `aaplimg.com` that start with `ocsp`) and how (TCP port 443). It is not counted as the app's egress. Everything else stays as strict as before: another name or service, another port or transport, the same check made for another process, a connection to an OCSP address that the app or one of Sparkle's helpers (`Autoupdate` included) makes on its own socket, or the same check outside an install fails. The check is not blocked. The privacy page says it in both languages: when an update installs, macOS may check the update's signature with Apple, and the app sends no data in that check. | `spec/02-platform.md` PLT-R906, section 9 acceptance and section 13.7; `spec/03-product.md` principle 4; the privacy page (`privacy` in `site/content/vi/pages.mjs` and `site/content/en/pages.mjs`, last updated 23/11/2026); [release](../runbooks/release.md) section 2 and [integration suite](../runbooks/integration-suite.md) section 5. The install check of the scripted test (`egress-update`, advisory until this decision) is to be aligned with section 13.7 in `scripts/vm/` and [VM test lab](../runbooks/vm-test-lab.md) section 12, a separate change |

## For the record

On the same day the product owner decided that {{AppName}} stays a macOS app for now: a Windows version may come
later if the Mac version gets many users, and Linux is not planned. The specification already targets macOS only
(`spec/03-product.md` PRD-R3 lists Windows and Linux among the non-goals), so nothing changes.

## Consequences

- The egress test of a release candidate covers the install too. A revocation check passes only in the form and the
  window that section 13.7 names; a later macOS or Sparkle that makes it another way (another name, port or
  process) fails the test until the specification names that form.
- Before the stable 1.1.0, the open items are the ones that [0508](0508-release-1-0-1.md) and the
  [1.1.0 provenance report](../provenance/reports/2026-11-19-1.1.0.md) list, without the rollback rehearsal. The
  provenance report is a dated record and is not edited; this record answers its line on QA-R39.
- The privacy page reaches the website with the next site deploy ([site deploy](../runbooks/site-deploy.md)
  section 6).
