# 04. Quality, release and support

Prefix: QA-R

This file defines how {{AppName}} is tested, built, signed, released, rolled back and supported, and how outside contributions are accepted. It is written for a single maintainer (Pa), so every process here must be cheap to run and hard to skip. Product behaviour is in `03-product.md` (PRD-R), typing rules in `01-engine.md` (ENG-R), macOS integration in `02-platform.md` (PLT-R), provenance in `05-clean-room.md` (CLR-R). Status: draft, 2026-11-13, adversarial review applied (performance gates and corpus names aligned with the engine and platform specs).

Placeholders: `{{AppName}}`, `{{app-slug}}` (bundle ID `vn.kal.{{app-slug}}`, cask `{{app-slug}}`, site `{{app-slug}}.kal.vn`).

## 1. Quality goals

| Goal | Measure | Gate |
|---|---|---|
| Never crash or hang on any key sequence | Fuzz hours without a finding; crash reports | Any engine crash or hang found by fuzzing blocks release |
| Never lose or duplicate text in Tier 1 apps | Compatibility script results | Any Tier 1 failure blocks stable release |
| Never lose settings or permissions on update | Upgrade test results | Any loss blocks release |
| Typing latency imperceptible | Performance benchmarks | Regression beyond thresholds (section 2.5) blocks merge |
| Support loop closes | Reopen rate, verified-fix rate | Reviewed monthly; reopen rate over 10% triggers a process review |

## 2. Test strategy

### 2.1 Layers

QA-R1 The repository MUST have these test layers, each runnable with one command documented in `CONTRIBUTING.md`:

1. **Engine unit tests** (Swift Testing) in the engine package: pure input to output, no AppKit, no I/O.
2. **Engine corpus tests**: table-driven files in `Tests/Corpus/` (section 2.2).
3. **Engine property and fuzz tests** (section 2.3).
4. **App logic tests**: settings migration, per-app rule resolution, hotkey recogniser, macro matcher, importers, diagnostics redaction. Platform services are injected behind protocols so these run without permissions.
5. **Platform integration tests**: real event pipeline against a bundled test host app (section 2.4). Require granted permissions, so they run on a dedicated machine.
6. **Compatibility checks**: scripted manual or semi-automated runs against real third-party apps (section 2.6).
7. **Upgrade tests**: install previous stable, configure, update through Sparkle, verify (section 3.6).

QA-R2 Line coverage: engine package MUST be at least 95%; app logic modules at least 80%. Coverage is reported per PR; a drop of more than 1 point fails the check.

QA-R3 Every bug fix MUST add a failing test first (engine corpus line, app logic test or compatibility script step) that references the issue number, then the fix. A PR that fixes a bug without a test is not merged unless the PR explains why it cannot be tested and adds a compatibility script step instead.

### 2.2 Engine corpus

QA-R4 The corpus MUST be data files (one case per line: method, options, keystrokes, expected output, expected restore output), human-readable and diffable. Categories, each a separate file:

| File | Content | Source |
|---|---|---|
| `syllables-telex`, `syllables-vni` | Every valid Vietnamese syllable (all onsets x rhymes x six tones that the orthography allows), lowercase, capitalised and all caps, in at least three keystroke orders: tone last, tone right after the vowel, tone after the final consonant | Generated by a script from the rule tables in `01-engine.md`; the generator is itself tested |
| `rhymes-rare` | Rare and edge rhymes: `uych` (huých, huỵch), `uơ` (huơ, thuở), `oong`, `ooc`, `uyu`, `oeo`, `quởn`, `gi` + vowel cases (gìn, giữ, giếng, giếc, giuộc), `qu` + vowel cases (quý, quờ, quạu), open `y` after `th` (Thy) | Orthography references (`01-engine.md` sections 3.7 to 3.10) |
| `no-shortcuts` | Sequences that Quick Telex products rewrite MUST stay as typed: `cc`, `kkk`, `nn`, `tt`, `gg`, `TT`, `pp`, `qq`, `uu` (ENG-R121, REG-04) | Hand curated |
| `macros` | Shortcut matching with a fixture table: letters-only, digit and punctuation shortcuts (`vn`, `k1`, `@@`, `ad.`), casing (`vn`, `Vn`, `VN`), terminator kept, no expansion of a longer shortcut's prefix, Backspace plus restore brings the shortcut back (`01-engine.md` section 11) | Hand curated |
| `proper-nouns` | Names and place names including ethnic-minority and loan forms: Buôn Ma Thuột, Krông Pắc, Đắk Lắk, Ea Kar, Pleiku, Kon Tum, Mù Cang Chải | Public gazetteers (record licence per CLR-R6) |
| `english` | English words and tech terms that MUST restore unchanged: text, user, case, wifi, USB, with, this, year, your, our, their, early, traffic, current, issue, google, github, iphone, macOS | Permissive word list (CLR-R6) plus a hand list of tech words |
| `collisions` | Strings that are both valid Vietnamese and English (`ma`, `me`, `to`, `an`, `hai`) with the expected policy outcome | Hand curated |
| `editing` | Backspace sequences, editing after `, ` `. ` and double space (previous word edit context must be recoverable), Return and Tab (they clear the history, so Backspace does not reopen the previous word: `01-engine.md` ENG-R912), tone changes on a finished word, removing marks (`z` / `0`) | Hand curated |
| `crash-regressions` | Every sequence that ever crashed any Vietnamese engine publicly: Telex `quz`, `QUZ`, `qqz`, `qutz`, `Quzhou`; VNI `qu0`, `qut0`; tokens of 33, 64, 256 and 4,096 keystrokes with and without marks; long runs of a single key; alternating tone keys | Public bug reports |
| `restore-exact` | Restore must reproduce typed keys exactly: VNI digits stay digits (`ba6c3` restores to `ba6c3`), doubled letters stay doubled (`traffic`, `current`), case preserved | Hand curated |
| `layouts` | Same cases keyed through QWERTZ, AZERTY, Dvorak and Colemak character mappings | Generated |
| `issues/<n>` | One file per fixed issue | Bug reports |

QA-R5 The corpus MUST run on every PR on both macOS and Linux (the engine package has no AppKit dependency, see `01-engine.md`), so the engine stays portable and Linux runners keep CI cheap.

QA-R6 A corpus case may only change its expected output in a PR labelled `corpus-change`, with the reason in the PR description. Bulk regeneration of expected values without review is forbidden.

QA-R68 The W11 collision corpus and its three adversarial sets (`01-engine.md` 13.11) run in CI as engine tests with the thresholds of ENG-R876 and ENG-R877; any wrong revision fails the build. The sets are fixtures in the engine package; a change to a bundled list that moves a number is reviewed with the list. *(Added on 15/11/2026 with the collision rules: the fixtures, the host-mode replay and the memory simulation are the `CollisionCorpusTests` target, run as their own step on Linux and inside the engine coverage run on macOS; `docs/decisions/0008-collision-learning.md`.)*

### 2.3 Property tests and fuzzing

QA-R7 Properties checked for random key sequences (letters, digits, punctuation, backspace, ESC, modifiers, both methods, all option combinations):
- P1 No crash, no trap, no precondition failure.
- P2 Each keystroke is processed within 1 ms on the CI machine (hang detector).
- P3 Engine memory per session stays bounded regardless of sequence length.
- P4 Applying the engine's edit commands (delete N, insert S) to a simulated text buffer always equals the engine's own view of the current text.
- P5 Output is valid Unicode NFC.
- P6 Restore of the current word yields exactly the keystrokes typed for that word.
- P7 With Vietnamese mode off, output equals input.

QA-R8 Fuzzing runs in two places (event counts per `01-engine.md` section 13.6):
- Per PR: property tests over at least 1,000,000 random events from fixed seeds (with and without a random macro table) plus 60 seconds of coverage-guided fuzzing (libFuzzer via `-sanitize=fuzzer` on a Linux runner, since the Linux Swift toolchain ships libFuzzer; VERIFY the current toolchain flags).
- Nightly: at least 100,000,000 random events and 30 minutes per method of coverage-guided fuzzing with AddressSanitizer and UndefinedBehaviorSanitizer; new findings open an issue automatically with the minimised input; the minimised input is added to `crash-regressions` when fixed.

QA-R9 The fuzz corpus (seed inputs) is stored in the repository and minimised monthly.

### 2.4 Platform integration tests

QA-R10 The repository MUST contain a test host app with: a native text field, a native text view, a WKWebView page with `input`, `textarea` and `contenteditable` elements, a simulated address bar with inline autocomplete, and a simulated spreadsheet cell editor. Each exposes its current text to the test runner.

QA-R11 Integration tests post synthetic key events through the real pipeline (as `02-platform.md` defines) into the test host and assert the final text, for at least: the 200 most common Vietnamese words in both methods, English restore samples, backspace across punctuation, fast typing at 15 keys per second, toggle hotkey, per-app rule switching between two host windows, macro expansion with a letters-only and a punctuation shortcut (`vn`, `@@`), restore hotkey consumed once and passed through on the second press, Secure Input on and off, tap disable and recovery (engine state MUST be reset after recovery), permission revoked mid-session (MUST fail open).

QA-R12 Integration tests run on a self-hosted macOS runner (a Mac under Pa's control with permissions pre-granted to the test build's stable signing identity; decided on 18/11/2026: a tart macOS virtual machine on Pa's Mac, usable at any time after a check that the host has free CPU, memory and disk, while Linux jobs stay on GitHub-hosted runners) on every merge to `main` and before every release. *(Amendment of 2026-11-18, the product owner's decision, `docs/decisions/0009-pa-decisions-2026-11-18.md`: the runner was proposed on 13/11/2026 and awaited confirmation. While the GitHub Actions workflows stay disabled, the suite runs in that virtual machine by hand, `docs/runbooks/integration-suite.md` and `docs/runbooks/vm-test-lab.md`.)* VERIFY whether GitHub-hosted macOS runners can grant Accessibility/Input Monitoring to a test binary (TCC database edits are possible on some images); if yes, also run a subset per PR.

QA-R13 The self-hosted runner MUST only run workflows from `main` and release tags of this repository (never pull requests from forks), because it holds granted permissions.

### 2.5 Performance regression gates

QA-R14 Benchmarks run on the same runner class each time, median of 5 runs, results stored as JSON artefacts and compared to the baseline file in the repository. The numbers live in exactly two places and this file does not repeat them:

| Layer | Single source of the budget | Gate |
|---|---|---|
| Engine time per event (corpus replay, hosted CI) | ENG-R1230: p50 at most 5 µs, p99 at most 25 µs, p99.9 at most 100 µs on M1-class Apple silicon | Fail if over budget or more than 20% slower than baseline after calibration (ENG-R1233) |
| Platform metrics: tap callback (T1), decide-to-posted (T2, T3), end-to-end delta (T4), held wait (T5), focus refresh (T6), idle and typing CPU (C1, C2), memory at rest and soak growth (M1, M2), ready after launch (S1) | `02-platform.md` section 8.1 table, "Gate" column | Fail if over the gate or more than 25% worse than baseline (PLT-R822); hosted subset per merge, self-hosted subset nightly |

QA-R15 The baseline file changes only in a PR labelled `perf-baseline` with the reason.

QA-R16 A nightly soak test replays 1,000,000 keystrokes through the integration pipeline and checks text correctness, memory growth and absence of stuck modifiers.

### 2.6 Compatibility matrix maintenance

QA-R17 Compatibility data is two versioned files in the repository, both owned by `02-platform.md`: `compat/rules.json` (shipped as `compat-rules.json`, behaviour per field, PLT section 5) and `compat/matrix.json` (verification status, PLT section 13.3). `compat/matrix.json` is the single source for the in-app Apps page and the website matrix (PRD-R35, PRD-R38). Each matrix entry records: bundle ID, display name, category, tier (per PRD-R39), matched rule ID, status, user-facing note, last verified date, app version, macOS version, verifier, linked issues.

QA-R18 A standard compatibility script (`compat/SCRIPT.md`) defines 12 steps that take under 3 minutes per app: type a Vietnamese paragraph with all tones in Telex; same in VNI; type `text user wifi USB`; edit a word after `, `; delete and retype the first character of a line; type in the first character of an empty field; type at 15 keys per second; use the toggle hotkey; expand a macro; check that autocomplete (if any) is not duplicated; check undo (Command+Z) restores sensible text; confirm no stray invisible characters (paste result into a hex viewer).

QA-R19 Cadence: Tier 1 re-verified for every stable release candidate, and every Tier 1 row at most 90 days old at release time (`02-platform.md` PLT-R531, the release gate); Tier 2 every minor release; all entries re-verified after each macOS major and point release that touches input (first beta and GM). Entries not verified for 120 days automatically display as `Chưa kiểm tra` on the website and in the next app build.

QA-R20 Community verifications are accepted through the `Compatibility report` issue form and recorded with the reporter's handle; a maintainer confirms before status becomes `Hoạt động tốt`.

QA-R21 A new per-app profile MUST come with a test in the integration suite that reproduces the app's behaviour in the test host (for example "address bar with inline autocomplete"), not only a data entry, so the behaviour is covered by CI.

### 2.7 Acceptance

- CI on a PR runs lint, build, engine corpus (macOS and Linux), app logic tests, coverage, property tests and short fuzz, in under 15 minutes.
- A deliberately injected crash on `quz` is caught by the corpus and by the fuzzer.
- A deliberately injected 30% slowdown in the engine fails the performance gate.
- A deliberately wrong collision rule threshold or bundled collision-list entry fails the QA-R68 gate.

## 3. CI and release

### 3.1 Continuous integration (GitHub Actions)

QA-R22 Workflows:

| Workflow | Trigger | Runner | Jobs |
|---|---|---|---|
| `ci.yml` | pull_request, push to main | GitHub-hosted macOS (latest stable image with the pinned Xcode) and Ubuntu | swift-format lint, build universal Debug, engine tests + corpus (macOS and Linux), app logic tests, coverage report, property tests, 60 s fuzz (Linux), benchmark compare (engine only) |
| `integration.yml` | push to main, release tags, manual | Self-hosted macOS | platform integration tests, soak (nightly), end-to-end benchmarks |
| `nightly.yml` | schedule | Ubuntu + macOS | 30-minute fuzz per method with sanitizers, dependency audit, stale compatibility report |
| `release.yml` | push of tag `v*` | GitHub-hosted macOS, `release` environment | section 3.3 |
| `site.yml` | push to main affecting `site/` or `compat/` | Ubuntu | build and deploy the website and compatibility matrix |

QA-R23 Pin the Xcode version explicitly (via `xcode-select` on a runner image that ships it) and record it in build metadata. VERIFY available runner labels (for example `macos-26`) and whether a macOS 27 image exists at implementation time; the app MUST be tested on the newest macOS release available, on the self-hosted runner if GitHub has no image.

QA-R24 Supply-chain hygiene: all third-party actions pinned by full commit SHA; Dependabot for actions and SwiftPM; `Package.resolved` committed; Sparkle is the only runtime dependency unless a decision record adds another; `pull_request_target` is never used; workflow permissions default to `contents: read`.

QA-R25 Branch protection on `main` and `prod`: no force push and no deletion; changes reach `main` as merge commits made with `--no-ff`, never squashed or rebased, so every branch keeps its commits (CLR-R12); required status checks from `ci.yml` once its jobs run again; signed commits from the maintainer recommended, and required once commit signing is set up. Releases are cut from `main` (or from a `release/x.y` branch for patch releases of an older minor). *(Amendment of 2026-11-18, integrator's call under the product owner's delegation, `docs/decisions/0009-pa-decisions-2026-11-18.md`: the text asked for linear history and required signed commits. Linear history would force squash or rebase merges, which CLR-R12 rules out for this project's evidence of independent creation; the repository has protected `main` and `prod` against force pushes and deletions since 15/11/2026, and no signing key is set up yet.)*

### 3.2 Versioning and channels

QA-R26 The app uses Semantic Versioning for `CFBundleShortVersionString`: MAJOR for breaking changes to settings format or minimum macOS, MINOR for features, PATCH for fixes. Pre-releases use `X.Y.Z-beta.N`. `CFBundleVersion` is a single integer that increases with every build published to any channel; Sparkle compares this value.

QA-R27 The engine package is versioned separately with its own SemVer and changelog; its public API changes follow SemVer strictly.

QA-R28 Two channels: Stable (default) and Beta. Beta items are tagged with the Sparkle channel `beta` in the same appcast or a separate feed (platform spec decides); Beta users also receive stable releases that are newer than the latest beta.

QA-R29 Cadence target: beta whenever there are user-visible fixes (typically weekly to biweekly during beta stages), stable roughly monthly after 1.0, hotfix any time. A stable release MUST have been on beta for at least 72 hours with no new P0/P1 regression, except hotfixes for P0. The 72 hours count from the publication of the latest beta of that version on the beta channel; while the user base is small there is no minimum number of beta users, installs or update checks. *(Amendment of 2026-11-18, the product owner's decision, `docs/decisions/0009-pa-decisions-2026-11-18.md`: 1.0.1 ships as a beta first, then as stable.)*

### 3.3 Build, sign, notarise, staple

QA-R30 The release process MUST, in order (CI runs the tests and the unsigned build; signing, notarisation and publication run on Pa's Mac, decision of the product owner, 13/11/2026, docs/decisions/0005-pa-decisions-2026-11-13.md):
1. Re-run the full `ci.yml` suite on the tagged commit and require the latest `integration.yml` run on that commit to be green. A release pipeline without a test gate is how a predecessor shipped an auto-update that left users unable to type.
2. Build a universal Release archive with hardened runtime, no `get-task-allow`, no unnecessary entitlements, signed with Pa's Developer ID Application certificate.
3. Verify signature (`codesign --verify --deep --strict`) and that the designated requirement matches the previous release's (bundle ID `vn.kal.{{app-slug}}` and Team ID unchanged). A changed designated requirement makes macOS re-ask permissions, so it is a hard failure.
4. Create the DMG (app plus Applications link, the licence text and the third-party notices, background, signed).
5. Notarise with `notarytool` using an App Store Connect API key (not an app-specific password), wait for the result, fail on any issue in the log.
6. Staple the ticket to the app and the DMG; validate with `stapler validate` and `spctl --assess`.
7. Produce SHA-256 checksums (and a build provenance attestation for the steps that run in GitHub Actions).
8. Upload the notarised DMG and update archive to `{{app-slug}}.kal.vn`, the only host for archives (`02-platform.md` PLT-R906).

QA-R31 Signing material stays on Pa's Mac (decision of the product owner, 13/11/2026): Developer ID signing and notarisation run there, and CI builds stay unsigned. If signing ever moves to CI, the material lives only in the GitHub `release` environment, which requires manual approval by Pa for each run and is restricted to tags on protected branches, and certificates are imported into a temporary keychain that is deleted at the end of the job.

QA-R32 The Sparkle EdDSA private key MUST NOT be stored in CI. The final step (signing the update archive with Sparkle's `sign_update` and publishing the appcast entry) runs on Pa's Mac with the key in the login Keychain, via a documented script `scripts/publish-release`. Rationale: a compromised GitHub account or workflow then cannot push a malicious auto-update. The private key has an offline encrypted backup in two places. The product owner accepted this manual step on 13/11/2026.

QA-R33 The EdDSA public key and feed URL are fixed in the app from the first public build. Key rotation requires a release signed with the old key that ships the new key, documented in a runbook.

### 3.4 Appcast and Homebrew

QA-R34 Appcast entries MUST include: `sparkle:version` (build integer), `sparkle:shortVersionString`, `sparkle:minimumSystemVersion`, EdDSA signature and length, release notes link in both languages, and `sparkle:channel` for betas. Use `sparkle:criticalUpdate` only for security or data-loss fixes.

QA-R35 Stable releases SHOULD use Sparkle phased rollout (`sparkle:phasedRolloutInterval`, for example 24 hours per group) so a regression reaches a fraction of automatic installs before everyone; manual "Check for updates" gets the release immediately. Hotfixes for P0 MAY skip phasing.

QA-R36 Homebrew: until the app meets the official homebrew-cask notability requirements (VERIFY current thresholds), publish the cask in Pa's own tap (`brew install --cask <owner>/tap/{{app-slug}}`), updated automatically by the release script. After notability, submit to the official homebrew-cask repository and rely on its autobump with `livecheck` pointing at the appcast. The cask MUST declare `auto_updates true`, the minimum macOS, and `zap` paths for the app's preferences, caches and application support folders (exact paths from the platform spec).

QA-R37 The website download page and changelog are updated by the same script that publishes the appcast, so the three never disagree.

### 3.5 Rollback

QA-R38 If a release is bad:
1. Remove its item from the appcast (stops further automatic installs within one check interval). This is the first action, within 1 hour of a confirmed P0.
2. Publish a pinned issue and a website banner describing the symptom and the workaround.
3. Ship a fix as a new, higher version. Sparkle does not downgrade, so a rollback is published as a new build number containing the previous good code (for example 1.4.1 built from 1.3.2 plus the version bump).
4. Keep every previous DMG downloadable from the archive page so a user can reinstall manually; reinstalling an older version MUST keep settings (settings schema is backward-readable for one MINOR version; newer unknown fields are preserved, not dropped).

QA-R39 The release runbooks MUST document the rollback procedure of QA-R38 and `02-platform.md` PLT-R1107 (`docs/runbooks/rollback.md`). A rehearsal of it on the beta channel is an optional drill, not a release gate: the maintainer SHOULD run one when they judge it useful, for example before a release that changes the update pipeline (the Sparkle version, the appcast, signing or the archive host), and records it in the runbook. No release waits for a rehearsal. *(Amendment of 2026-11-23, the product owner's decision, `docs/decisions/0011-pa-decisions-2026-11-23.md` item 3: the text asked for a rehearsed rollback, executed once on the beta channel before public beta; it was waived for 1.0 (`docs/decisions/0507-first-public-release-1-0.md`) and listed as open for the stable 1.0.1 and 1.1.0. The procedure itself is unchanged.)*

### 3.6 Update safety

QA-R40 Upgrade test before every release, on the self-hosted runner or a clean VM: install the previous stable from its DMG, grant permissions, change at least 10 settings, add per-app rules and 50 macros, then update through Sparkle to the release candidate. Verify: settings, rules, memory and macros identical; permissions still granted (no prompt); typing works in the test host within 5 seconds of relaunch.

QA-R41 Settings migrations are versioned, run once, back up the previous settings file next to the new one before migrating, and are covered by fixture tests for every previously shipped schema version.

QA-R42 On first launch after an update, the app runs a self-check (permission state, tap creation, a synthetic round-trip in an off-screen field if the platform spec allows) and, on failure, shows the targeted permission screen (PRD-R42) instead of failing silently.

### 3.7 Release checklist (summary)

Corpus and fuzz green; integration green on newest macOS; Tier 1 compatibility script done for this RC; upgrade test passed; changelog written in Vietnamese and English with app names; provenance review done for first public and 1.0 releases (CLR-R13); notarised and stapled; appcast signed locally; Homebrew updated; website updated; pinned announcement for notable changes.

## 4. Issue policy

### 4.1 Templates

QA-R43 Use GitHub issue forms; blank issues disabled. Questions go to GitHub Discussions. Forms:

| Form | Required fields |
|---|---|
| **Bug report** | App where it happens (name and version); what was typed and what appeared (user types it in again; the form says not to paste private text); symptom chips (lost letters, duplicated letters, wrong tone, cannot type Vietnamese, lag, other); diagnostics block (pasted from the in-app report, PRD-R47); does it happen in the {{AppName}} practice field (yes/no) |
| **Compatibility report** | App, version, macOS version, result of each step of `compat/SCRIPT.md`, diagnostics block |
| **Feature request** | Problem first, then proposed behaviour; persona; "is this a default change or a new setting?" |
| **Security** | Not an issue form: links to the private reporting path (section 6) |

QA-R44 The diagnostics block format is stable and machine-parseable (a fenced block with a header line containing the format version) so a GitHub Action can parse it and auto-apply labels (`app:<bundle>`, `macos:<major>`, `arch:arm64|x86_64`, `method:telex|vni`).

### 4.2 Labels

QA-R45 Label set:
- Type: `bug`, `compat`, `feature`, `docs`, `question`.
- Area: `area:engine`, `area:injection`, `area:hotkey`, `area:per-app`, `area:ui`, `area:onboarding`, `area:update`, `area:permissions`, `area:macros`, `area:site`.
- App: `app:<name>` (auto from diagnostics).
- Priority: `P0` (cannot type, data or text loss across apps, machine freeze, security, settings loss on update), `P1` (Tier 1 app broken or common sequence wrong), `P2` (Tier 2 app or rare sequence), `P3` (cosmetic).
- Status: `needs-info`, `confirmed`, `fixed-in-beta`, `fixed-in-release`, `verified`, `closed-unverified`, `wontfix`, `known-limitation`.
- Resolution tags for metrics: `resolution:setting-workaround`, `update-regression`, `reopened`.

### 4.3 Lifecycle

QA-R46 An issue is NOT closed when a fix is merged. Lifecycle:
1. `confirmed` after reproduction (with a failing test linked).
2. Fix merged: `fixed-in-beta` with the beta version; comment asks the reporter to try that beta (with the one-click channel switch instructions).
3. Stable shipped: `fixed-in-release` with the version.
4. Close as `verified` when the reporter (or another affected user) confirms; or close as `closed-unverified` after a grace period of 14 days after `fixed-in-release` with no response, with a comment explaining how to reopen.
5. If the reporter says it is still broken, the maintainer reopens, adds `reopened`, and the next fix must add a new test that reproduces the remaining failure.

QA-R47 No bot reopens issues on any comment; no bot closes issues for inactivity while they are `confirmed`. `needs-info` issues close after 21 days without the requested information, with a friendly comment.

QA-R48 Answers of the form "turn on setting X" MUST be tagged `resolution:setting-workaround`, and each such tag opens a follow-up task: either change the default, fix the behaviour, or improve the setting's explanation.

QA-R49 Maintainers MUST NOT ask end users for verbose logs or terminal commands as a first step; the in-app report and the practice-field check come first. Developer-level instructions are a last resort, written step by step.

QA-R50 Metrics reviewed monthly from the GitHub API with a small script committed in `scripts/`: reopen rate (target under 10%), verified versus unverified closes, median time to first response, median time to fix by priority, share of `compat` issues, count of `resolution:setting-workaround`.

## 5. Support loop for a one-person maintainer

QA-R51 Channels: GitHub Issues (bugs, compatibility), GitHub Discussions (questions, ideas), support email for users without GitHub (one project mailbox on `kal.vn` for support, security and conduct, decided on 13/11/2026; the address lives in the brand files, `APP_SUPPORT_EMAIL`). No support by private message on social networks; the website says so politely and links to the channels.

QA-R52 Response targets (published on `/ho-tro`; business days, best effort, stated honestly as targets):

| Priority | First response | Resolution target |
|---|---|---|
| P0 | 24 hours | Appcast pull or workaround within 24 hours of confirmation; fix or rollback release within 72 hours |
| P1 | 3 days | Next beta; next stable |
| P2 | 7 days | Planned in a milestone or labelled `known-limitation` with explanation |
| P3, features | Monthly triage | Answered with accept, decline with reason, or "later" |

QA-R53 Routine: one fixed weekly triage session (labels, priorities, saved replies, compatibility queue) and one release-preparation session. Feature requests are reviewed monthly in one batch. Saved replies for common topics (permission, Secure Input, other IME running, app known limitation, how to switch to beta) live in `docs/support/replies.md` in both languages.

QA-R54 When Pa is unavailable for more than a week, set a banner on the website and a pinned issue with the expected return date; P0 handling during absence is limited to pulling the appcast item.

QA-R55 Every support conversation that reveals a confusing UI or missing doc becomes an issue labelled `docs` or `area:ui`; recurring questions become FAQ entries within the next release cycle.

## 6. Security disclosure

QA-R56 `SECURITY.md` MUST describe: supported versions (latest stable and latest beta), how to report privately (GitHub private vulnerability reporting enabled on the repository, plus the project mailbox on `kal.vn`, `APP_SUPPORT_EMAIL` in the brand files), what to include, and the response process.

QA-R57 Process: acknowledge within 72 hours; triage severity within 7 days; fix target 30 days for high or critical, 90 days for others; coordinated disclosure with credit to the reporter unless they decline; publish a GitHub Security Advisory (with a CVE through GitHub when warranted); ship as a critical update (QA-R34).

QA-R58 In scope: anything that could expose typed content (logging, diagnostics, crash reports, IPC), update chain integrity (feed, signatures, download), code signing and permission handling, settings import parsing, website and appcast hosting. Out of scope: issues requiring an already compromised user account with the same privileges, social engineering, denial of service against the website.

QA-R59 Security-sensitive PRs (event handling, diagnostics, import parsers, updater configuration, release scripts) require a dedicated security review checklist in the PR (no typed content logged, no new network endpoints, inputs validated, no new entitlements) before merge.

QA-R60 Any new network endpoint in the app requires a decision record and an update to `/rieng-tu` in the same PR. A CI check MUST fail if the binary contains URL hosts outside an allowlist (appcast host, website host, GitHub, mail link).

## 7. Contribution rules

QA-R61 Contribution sign-off follows the licence decision of the product owner (13/11/2026, amended 15/11/2026; `docs/decisions/0006-app-licence-and-pro-edition.md`): the engine packages, the `data/` pipeline and the reference model are MPL-2.0, everything else is GPL-3.0-or-later.
- Every contribution, in every area: Developer Certificate of Origin (`Signed-off-by` on every commit, the e-mail matching the commit author), enforced by a DCO check on pull requests. Rationale: lightweight and familiar to contributors.
- Inbound terms: a contribution to an MPL-2.0 part is licensed under MPL-2.0 and a contribution to a GPL-3.0-or-later part under the GPL, as part of the project; either is also licensed to the project under MIT, so the copyright holder can change the licences later without asking every contributor again (the Pro edition this grant first served was withdrawn on 15/11/2026); the sign-off affirms this. There is no CLA. `CONTRIBUTING.md` states these terms.

QA-R62 Every PR template includes a clean-room attestation checkbox: "I did not read or copy code from other Vietnamese input methods while writing this change (see spec/05-clean-room.md)." PRs from contributors who cannot tick it are declined politely.

QA-R63 PRs MUST: reference an issue (except typo fixes); include tests per QA-R3; pass CI; follow the formatting configuration; use English Conventional Commits (`type: description`); not add dependencies without a decision record; not add settings without a written justification against PRD principle 5.

QA-R64 AI-assisted contributions are allowed under the same rules; the contributor is responsible for provenance (CLR-R4).

QA-R65 A `CODE_OF_CONDUCT.md` (Contributor Covenant) applies to all project spaces.
